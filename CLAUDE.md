# MnemoToad — Project Conventions

## Git commit conventions
- No story numbers in commit messages (e.g. "Story 1.2"). Stories are self-generated by the user for
  their own planning, not a real tracker — a commit referencing one is a dangling reference to
  nobody else.
- Matter-of-fact, not verbose. List what changed, plainly. Skip rationale/motivation prose,
  "why this matters" framing, and other narrative padding.

## Solution layout
- `MnemoToad.Api` — ASP.NET Core Web API, .NET 10 (LTS), controllers (refactored off minimal APIs).
  `Program.cs` has no route mappings left — every endpoint, including `/health`, is a controller.
  `/health` is a controller (not minimal-API) because it's expected to grow (DB connectivity checks,
  etc.), not stay a static response.
- `MnemoToad.Data` — class library: entities (under `Entities/`), `AppDbContext` (which implements
  `IAppDbContext` — see "API patterns" below), and repositories (under `Repositories/`, e.g.
  `INodeTypeRepository`/`NodeTypeRepository`) that wrap `IAppDbContext` behind an interface. Holds
  the `Npgsql.EntityFrameworkCore.PostgreSQL` package reference directly
  (needed to catch `Npgsql.PostgresException` when translating constraint failures — see
  "Constraint-violation translation" below); `.UseNpgsql(...)`/`.UseSnakeCaseNamingConvention()`
  themselves are still called from `MnemoToad.Api`'s `ServiceCollectionExtensions.cs`, not here, via
  the transitive package reference that flows through the `MnemoToad.Api` → `MnemoToad.Data` project
  reference — `MnemoToad.Api`'s own `.csproj` has no direct `PackageReference` to the Npgsql
  provider. There is no service layer — controllers depend directly on repository interfaces (see
  "API patterns" below for why it was removed). This project stays entities + DbContext + repositories
  only, no business rules, with the one deliberate exception described below (repositories translating
  a known DB constraint into a `ValidationException`, which isn't pre-flight business logic, just a
  direct translation of a failure the DB already caught).
- `MnemoToad.DbMigrator` — standalone console app running DbUp against Postgres. NOT part of any
  project reference from the API; only shares the solution file.
- `MnemoToad.Karate` — Java/Maven, integration tests. Separate toolchain, not in the `.sln`, no
  impact on .NET build.
- `MnemoToad.Tests` — NUnit + Moq (not xUnit — switched deliberately). Three layers of coverage:
  controller tests mock the repository interface directly (no service layer left to mock), repository
  tests run against a real EF Core InMemory database, and system tests send real HTTP requests through
  the full app pipeline. See "Testing" below for the full pattern.

## Database (Postgres)
- **DbUp, not EF Core Migrations.** Deliberate choice — plain numbered `.sql` scripts in
  `MnemoToad.DbMigrator/Scripts/`, for full DDL flexibility (future table→view conversions, etc.).
- **Script numbers are append-only, forever**, once a script has run anywhere (including just
  locally). Never renumber, edit, or delete an applied script — add a new forward script instead
  (e.g. `DROP TABLE ...` in a new file, not editing the old `CREATE TABLE`).
- **One sanctioned exception:** once a table is fully retired — its `DROP` script confirmed applied
  in every known environment — the entire create/seed/.../drop script set for that table may be
  deleted together as a batch. A fresh environment reaches the same end state (table never existed)
  whether the scripts are present or not, so there's no consistency risk once every environment has
  converged. Don't renumber the scripts that remain; leave the gap. First done for the retired
  `country` table (scripts `001`, `002`, `005`). Scripts currently run `003`–`004`, then `006`
  onward — `005` stays reserved/skipped rather than reused, per the same "leave the gap" rule.
- `CreatedUtc`/`ModifiedUtc` columns (first used on `knowledge_node`) are DB-populated, not
  entity-mapped — the C# entity has no property for them at all. `created_utc` uses a column
  `DEFAULT (now() AT TIME ZONE 'utc')`; `modified_utc` needs the same default (for insert) plus a
  `BEFORE UPDATE` trigger (a column default only fires on `INSERT`). The trigger function
  (`set_modified_utc()`, script `006_CreateSetModifiedUtcFunction.sql`) is written generically so
  future tables needing the same behavior can attach their own `BEFORE UPDATE ... EXECUTE FUNCTION
  set_modified_utc()` trigger without redefining the function. Consequence: no .NET-level test
  (mocked repository, or the EF Core InMemory provider used by repository/system tests) can assert
  timestamp behavior at all, since neither the entity nor InMemory ever touches those columns — that
  coverage can only happen where a real Postgres instance is involved (Karate), and Karate currently
  has no way to read column values back (see "No passthru" note below).
- Tables/columns: `snake_case` in Postgres. `EFCore.NamingConventions` +
  `.UseSnakeCaseNamingConvention()` on the DbContext maps PascalCase C# automatically — don't
  hand-write `ToTable`/`HasColumnName` unless overriding the convention.
- Two DB roles: a scoped admin (owns the `mnemotoad` database, runs DbUp/DDL) and a low-privilege
  `postgres` app role (SELECT/INSERT/UPDATE/DELETE only — no ALTER/DROP, which Postgres doesn't
  allow via GRANT anyway). The running API connects as the low-priv role; DbUp connects as admin.
- `ALTER DEFAULT PRIVILEGES` scripts omit `FOR ROLE` (defaults to current role) — keeps admin
  username out of source control and portable across environments.
- DB/role bootstrap (`CREATE DATABASE`, `CREATE ROLE`) is NOT a DbUp script — it can't be, since
  DbUp's connection string already targets the database. It's a one-time manual `psql` step per
  new server, before `DB_CONNECTION_STRING` has a valid target.

## Connection strings
- Each project (`MnemoToad.Api`, `MnemoToad.DbMigrator`) has its OWN `appsettings.Development.json`
  — not shared/copied between them (deliberate: local dev envs may want to vary per project).
- `DbMigrator`'s config lookup uses `SetBasePath(AppContext.BaseDirectory)`, and the `.csproj` copies
  it via a **glob** (`<None Include="appsettings*.json">`), not a literal filename — a literal
  filename fails the CI build (`MSB3030`) when the gitignored file doesn't exist there; a glob just
  matches nothing and passes silently.
- Priority chain in `DbMigrator`: explicit CLI arg > `DB_CONNECTION_STRING` env var (CI/Azure) >
  `appsettings.Development.json` (local).
- `WithScriptsFromFileSystem` also needs a path built from `AppContext.BaseDirectory` — a bare
  `"Scripts"` string resolves against the process's current directory, which differs between local
  runs and CI.

## CI/CD (GitHub Actions)
- **`pipeline.yml` is the single push-triggered entry point**, and the only file allowed to `uses:`
  the others. Every other workflow file (`build-api.yml`, `deploy-api.yml`, `restart-api.yml`,
  `db-deploy.yml`, `karate.yml`) has no standalone `push` trigger — only `workflow_call` (so
  `pipeline.yml` can invoke them) and `workflow_dispatch` (so each still runs standalone by hand).
  This refines the older "workflows are deliberately decoupled" rule — the individual files still
  don't reference *each other*, but `pipeline.yml` is deliberately the one orchestration layer
  permitted to compose them. Don't add `needs`/`uses` coupling directly between the subordinate
  files themselves.
- `pipeline.yml` uses `dorny/paths-filter@v3` to detect which of three areas changed — `api`
  (`MnemoToad.Api/**` + `MnemoToad.Data/**`, since `MnemoToad.Data` compiles into the API), `data`
  (`MnemoToad.DbMigrator/**`), `karate` (`MnemoToad.Karate/**`) — then routes via job
  `needs`/`if` conditions:
  - `api` changed → full pipeline: `build-api` → `db-deploy` (migrate) → `deploy-api` → `karate`
    (`@Smoke`, `azure`).
  - `data` changed (and not `api`) → `db-deploy` (migrate) → `restart-api` (bounce, no redeploy) →
    `karate`.
  - `karate` changed only → `karate` runs alone, no build/deploy/migrate.
  - Full order when `api` changed: `build-api` → `unit-tests` → `db-deploy` (migrate) →
    `deploy-api` → `karate`.
  - Conditional jobs use `always() && !cancelled()` plus explicit `needs.<job>.result` checks (not
    the default `success()` gate), since a job upstream may have legitimately been skipped rather
    than failed — GitHub Actions doesn't treat "skipped" as passing a plain `if: needs.x`.
  - `karate`'s guard checks every upstream job's result for `!= 'failure'` explicitly (not just its
    immediate `needs`) — checking only `deploy`/`restart-api` isn't enough, since those jobs get
    skipped (not failed) when an earlier job like `migrate` fails, and a skip looks identical to
    "wasn't needed" unless the whole chain is checked.
  - Job IDs with hyphens (`unit-tests`, `restart-api`) need bracket syntax in expressions —
    `needs['unit-tests'].result`, not `needs.unit-tests.result` (the latter parses as subtraction).
- `azure-deploy.yml` (fused build+deploy) was split into `build-api.yml` (build/publish/upload
  artifact) and `deploy-api.yml` (download artifact/deploy) so a unit-tests/migration step can sit
  between them. `deploy-api.yml` is `workflow_call`-only (no standalone `workflow_dispatch`) since
  it depends on an artifact a prior `build-api` job produced in the same run — it can't run alone.
- `build-api.yml` restore/build/publish are scoped to the API project explicitly
  (`MnemoToad.Api/MnemoToad.Api.csproj`), not the whole solution — otherwise `DbMigrator` gets
  bundled into the publish output.
- Azure auth is OIDC/federated credentials (`azure/login@v2`), not a publish profile.
- `deploy-api.yml` uses `clean: true` on `azure/webapps-deploy` to avoid stale files lingering in
  `wwwroot` across deploys.
- API's Azure connection-string app setting is pushed from a GitHub secret
  (`API_DB_CONNECTION_STRING`, the low-priv `postgres` role) via `azure/appservice-settings`, as
  `"name": "Default"` — separate from `DB_CONNECTION_STRING` (admin, used only by `db-deploy.yml`).
- `restart-api.yml` resolves the Azure resource group dynamically via `az webapp list --query
  "[?name=='...'].resourceGroup"` rather than hardcoding it — nothing in the repo names the resource
  group anywhere else.
- Both `deploy-api.yml` and `restart-api.yml` end with a "Wait for App Service to be healthy" step
  that polls the app's actual `/health` URL via `curl --fail`, up to 30 attempts / 10s apart, before
  the job is allowed to succeed. **The hostname is looked up dynamically** — `az webapp list
  --query "[?name=='...'].defaultHostName"` — same pattern as the resource-group lookup below, and
  for the same reason: don't assume, ask Azure. This app's real hostname is NOT
  `mnemotoad.azurewebsites.net` (an earlier version of this step wrongly assumed that classic
  `<name>.azurewebsites.net` pattern and every deploy failed on the health check as a result) — since
  June 2024 Azure App Service assigns "secure unique default hostnames"
  (`<name>-<hash>.<region>-01.azurewebsites.net`) to prevent subdomain-takeover attacks, this is now
  mandatory with no opt-out, and it can't be changed after the app is created or reclaimed via a
  custom-domain binding (you can't prove DNS ownership of a zone Microsoft controls). This app's
  actual hostname follows the `<app-name>-<hash>.<region>-01.azurewebsites.net` pattern and is
  hardcoded as-is in `karate-config.js`'s `azure` env baseUrl — that one stays hardcoded rather than
  dynamic since Karate config has no Azure CLI access at test-run time (see that file for the exact
  value).
  This lives at the end of each of those two workflows (not as a separate job in `pipeline.yml`)
  because it's what makes "deploy/restart succeeded" actually mean "the app is live," not just "the
  Azure API call returned 0" — `karate`'s existing `needs.deploy.result != 'failure'` /
  `needs['restart-api'].result != 'failure'` guards in `pipeline.yml` pick this up for free, no
  pipeline changes needed. Relies on `/health` staying an unauthenticated, cheap endpoint. Only
  polls one instance's DNS name — if the webapp ever scales to multiple instances behind the shared
  hostname, a single healthy response no longer proves every instance is ready, since Azure's load
  balancer could keep routing to a warm instance while a cold one is still starting; revisit then
  (e.g. per-instance health checks, or Azure App Service's built-in health check feature with
  `WEBSITE_HEALTHCHECK_MAXPINGFAILURES` to auto-evict unhealthy instances from the pool first).

## API patterns (controllers)
- Service registration (`AddControllers`, `AddSwaggerGen`, `AddDbContext`, `AddScoped<...>`, etc.)
  lives in `MnemoToad.Api/Configuration/ServiceCollectionExtensions.cs`, as an
  `AddApiServices(this IServiceCollection, IConfiguration)` extension method — not inline in
  `Program.cs`. Keeps `Program.cs` a thin composition root as registrations grow. The middleware
  *pipeline* (`UseSwagger`, `MapControllers`, etc.) stays inline in `Program.cs` — it's short enough
  to read at a glance and its call order matters, which is clearer left visible in one place.
- One controller per resource, named `<Entities>Controller` (plural, e.g. `NodeTypesController`),
  `[ApiController]` + explicit `[Route("<resourceName>")]` (camelCase, matching the existing URL
  convention — don't rely on `[Route("[controller]")]`'s PascalCase default).
- Services are injected via constructor (not `[FromServices]` — that was a minimal-API-only
  workaround for endpoint-lambda body-inference and no longer applies).
- **Dependencies are injected as interfaces, not concrete classes, all the way down to the
  DbContext** — `NodeTypesController` depends on `INodeTypeRepository` directly (no service layer in
  between — see below), and all four repositories depend on `IAppDbContext`
  (`MnemoToad.Data/IAppDbContext.cs`), not `AppDbContext` directly. `IAppDbContext` exposes the same
  surface `AppDbContext` always has — the four `DbSet<T>` properties plus a parameterless
  `SaveChangesAsync()` (added alongside the interface so callers don't need to pass a
  `CancellationToken` they never used) — and `AppDbContext` implements it directly, so no behavior
  changed, only what type repositories ask for in their constructor.
  `ServiceCollectionExtensions.cs` resolves it to the same scoped `AppDbContext` instance
  (`services.AddScoped<IAppDbContext>(sp => sp.GetRequiredService<AppDbContext>())`). **This reverses
  an earlier version of this rule that said not to add `IAppDbContext`**, reasoning that it'd be a
  redundant second layer over what the repository interface already provided — that reasoning was
  scoped to testing the *service* layer only (which mocks `INodeTypeRepository` and never touches
  `AppDbContext` at all, so it's still true `IAppDbContext` adds nothing there). It didn't account
  for wanting to unit-test the *repository* layer itself, which is what actually motivated adding
  it — see "Testing" below for how repository-level tests use it. Interfaces are entity-specific
  (`INodeTypeRepository`, not a generic `IRepository<T>`) — add a generic version only if a second
  entity's repository turns out to genuinely share logic with this one, not preemptively.
- Request DTOs live in `MnemoToad.Api/Contracts/` (e.g. `NodeTypeRequest`), one file per contract —
  not nested in the controller file.
- **There is no service layer.** An earlier version had `NodeTypeService`/`KnowledgeNodeService`/
  `RelationshipTypeService`/`KnowledgeRelationService` sitting between controllers and repositories,
  each with its own `Validate()` method (shape checks only — e.g. `Name`/`CanonicalName` not blank,
  `NodeTypeId != Guid.Empty`) plus a decision to let the DB own constraint questions
  (existence/uniqueness) rather than pre-flighting them with an extra repository round-trip. An even
  earlier version of `KnowledgeNodeService` checked `NodeTypeId` existence and
  `NodeTypeId`+`CanonicalName` uniqueness itself before writing, and `NodeTypeService` checked `Name`
  uniqueness and referencing `KnowledgeNode`s before delete the same way — each an extra `SELECT` per
  check, and still racy under concurrent writes — before both were replaced with just attempting the
  write and translating a constraint failure after the fact. Once every service had shrunk to "no
  orchestration beyond one repository call, plus shape validation," the whole layer was removed: shape
  validation moved to DataAnnotations on the request DTOs (`[Required]`, plus a custom
  `RequiredGuidAttribute` — plain `[Required]` doesn't reject `Guid.Empty` on a non-nullable `Guid`),
  enforced automatically by `[ApiController]`'s model-validation filter before the action even runs,
  returning a `ValidationProblemDetails` 400 with no controller code involved. Repositories collapsed
  each CRUD operation into a single `CreateAsync`/`UpdateAsync`/`DeleteAsync` call doing the full
  fetch → mutate → save unit of work itself (`SaveChangesAsync` became `private`), and controllers now
  depend on the repository interfaces directly. `KnowledgeRelationRepository` has no `UpdateAsync`
  (relations were never updatable) and dropped `GetByIdAsync` from its public interface (inlined into
  `DeleteAsync`, since nothing else needed it). **`DeleteAsync` on all four repositories was later
  collapsed further, from fetch-then-remove-then-save (a `SELECT` round-trip plus a
  `SaveChangesAsync` round-trip) to a single `_db.ExecuteDeleteAsync(_db.<Set>.Where(x => x.Id ==
  id))` call** — one DELETE statement, no fetch first. No `.Take(1)`/"limit 1" guard was added:
  `ExecuteDelete`/`ExecuteUpdate` don't allow `Take`/`Skip`/`OrderBy` at all (EF throws if you try),
  and since the predicate is always equality on the `Guid` PK, at most one row can ever match anyway.
  See "Testing" below for how this bypasses `SaveChangesAsync` (and what that meant for constraint-
  violation catches and for the test double). An "update where"-style approach for `UpdateAsync` is
  still a deliberately deferred follow-up (see below), not done yet.
- Controller actions catch `ValidationException` (thrown by the repository — see
  "Constraint-violation translation" below) and return
  `Problem(detail: ex.Message, statusCode: StatusCodes.Status400BadRequest)`, an RFC 7807
  `ProblemDetails` response — the same family as the automatic DataAnnotations
  `ValidationProblemDetails` 400 above, so both kinds of failure come back as the same status code
  and a compatible body shape (`errors` dictionary vs. `detail` string differ by necessity, since
  they represent different kinds of failures). Stays inline per-action (try/catch) rather than a
  global exception filter — revisit only if this pattern repeats across many more actions.
  `KnowledgeRelationsController.Delete` has no try/catch at all — deleting a `KnowledgeRelation` never
  violates a constraint, since nothing has an FK pointing back at it.
- PKs are `Guid`, generated app-side or via Postgres `gen_random_uuid()`.
- **Constraint-violation translation lives entirely in the repository — the DB error is caught and
  rethrown as `System.ComponentModel.DataAnnotations.ValidationException` right there, with no
  intermediate exception type and no service-layer catch.** `NodeTypeRepository.SaveChangesAsync()`,
  `KnowledgeNodeRepository.SaveChangesAsync()`, and `RelationshipTypeRepository.SaveChangesAsync()`
  each wrap their own `_db.SaveChangesAsync()` in a try/catch keyed on
  `Npgsql.PostgresException`/`SqlState` (`Npgsql.PostgresErrorCodes.UniqueViolation` /
  `ForeignKeyViolation`) and throw `new ValidationException("...")` with the entity-specific message
  directly (e.g. "A NodeType with that name already exists." / "The NodeType cannot be deleted
  because it is referenced by one or more KnowledgeNodes." / "A KnowledgeNode with the same NodeType
  and CanonicalName already exists." / "The specified NodeType does not exist."). No service has
  anything left to do with that exception — `ValidationException` propagates straight through
  `CreateAsync`/`UpdateAsync`/`DeleteAsync` to the controller's existing
  `catch (ValidationException) → BadRequest`. An earlier version of this routed through a
  `ConstraintViolationTranslator` helper plus two custom exception types
  (`UniqueConstraintViolationException`/`ForeignKeyViolationException`) in `MnemoToad.Data/
  Exceptions/`, with each service catching those and re-throwing its own `ValidationException` — that
  was deliberately simplified away (the extra hop added no behavior, just indirection) in favor of
  the repository owning the message text outright. Any other failure — an untranslated
  `DbUpdateException`, a connection failure when the DB is down, etc. — is deliberately left
  unhandled and propagates to the default ASP.NET Core `500`. Repositories throwing
  `ValidationException` here isn't the "business/validation logic" `MnemoToad.Data` is otherwise kept
  free of (see "Solution layout" above) — there's no rule being evaluated, just a known DB constraint
  failure translated into the vocabulary the controller already understands.
- **Delete-time FK-violation catches live in `DeleteAsync` itself, not in the shared
  `SaveChangesAsync()` wrapper** — a consequence of `DeleteAsync` no longer calling
  `SaveChangesAsync()` at all (see the `ExecuteDeleteAsync` bullet above). `NodeTypeRepository`'s FK
  catch (it has no FKs of its own, so any FK violation on it can only be a delete being blocked by a
  referencing `KnowledgeNode`) and `RelationshipTypeRepository`'s (`TableName: "knowledge_relation"`)
  moved there wholesale. `KnowledgeNodeRepository` is the one split case: `TableName: "knowledge_node"`
  (an invalid `NodeTypeId` on a write) stays in `SaveChangesAsync()` since that's still a create/update
  concern, while `TableName: "knowledge_relation"` (deleting a still-referenced `KnowledgeNode`) moved
  to `DeleteAsync`. `KnowledgeRelationRepository.DeleteAsync` has no catch at all, unchanged — nothing
  references a `KnowledgeRelation`, so its delete still can't violate a constraint.
  `IAppDbContext.ExecuteDeleteAsync<TEntity>(IQueryable<TEntity> query)` is what makes this
  catchable at all: `AppDbContext`'s implementation catches a raw `Npgsql.PostgresException` (that's
  what a Postgres-backed `ExecuteDeleteAsync()` throws — unlike `SaveChangesAsync()`, it does not wrap
  failures in `DbUpdateException`, since it bypasses the change-tracker/update pipeline entirely) and
  rethrows it wrapped in `DbUpdateException`, purely to keep the exception shape identical to what
  `SaveChangesAsync()` throws — so repositories' existing `catch (DbUpdateException ex) when
  (ex.InnerException is PostgresException {...})` pattern didn't need to change shape, only location.
- **`KnowledgeNode.CanonicalName` is unique per `NodeType`, not globally unique** — the same name can
  exist under different types (e.g. "Mercury" the planet vs. the element vs. Freddie Mercury are
  legitimately separate nodes, since each has a different `NodeTypeId`), but two nodes can't share
  both the same `NodeTypeId` *and* the same `CanonicalName`, enforced by the DB constraint above (see
  previous bullet for how a violation surfaces as a `400`). The whole point of `KnowledgeNode` is
  still that the `Guid`, not the name, is the identity — this constraint doesn't change that, it just
  scopes "duplicate" to within a type.
- **No separate single-column index on `knowledge_node.node_type_id`.** The composite unique
  constraint above already creates a btree index with `node_type_id` as the leading column, which
  Postgres can use directly for an equality lookup on `node_type_id` alone (e.g. `GET
  /nodes?nodeTypeId=...`, the "all nodes of a type" query) — a second single-column index would just
  be redundant write overhead. `IKnowledgeNodeRepository.GetAllAsync(Guid? nodeTypeId = null)` takes
  the optional filter directly (not a separate `GetByNodeTypeIdAsync` method) since it's the same
  query with or without the filter.
- **`KnowledgeRelation`** (script `009_CreateKnowledgeRelationTable.sql`) links two
  `KnowledgeNode`s through a `RelationshipType` — `SourceNodeId`/`TargetNodeId` FK to
  `knowledge_node(id)`, `RelationshipTypeId` FKs to `relationship_type(id)`, and a composite
  `UNIQUE (source_node_id, relationship_type_id, target_node_id)` (named
  `uq_knowledge_relation_source_type_target`) prevents the exact same triple existing twice — the
  same source/target pair under a *different* `RelationshipType` is allowed, same idea as
  `KnowledgeNode.CanonicalName` above. No `CreatedUtc`/`ModifiedUtc` on this table, matching
  `RelationshipType`'s precedent rather than `KnowledgeNode`'s — not every table gets those columns.
  Only three endpoints exist, per the story spec: `POST /relationships`, `DELETE
  /relationships/{id}`, `GET /nodes/{id}/relationships` (the last one lists relations where the node
  is either source or target — `IKnowledgeRelationRepository.GetByNodeIdAsync` matches on either
  column). No `GET /relationships` (list-all) or `GET /relationships/{id}` or `PUT` — a relation is a
  link, not an independently browsable or updatable resource. All three actions live in one
  `KnowledgeRelationsController` (`[Route("relationships")]`) — the nested-under-nodes `GET` action
  uses an absolute route override (`[HttpGet("/nodes/{nodeId:guid}/relationships")]`) rather than
  moving to `KnowledgeNodesController`, since it's still fundamentally listing `KnowledgeRelation`
  resources (one controller per *resource type*, not per URL prefix).
  - **This is the first entity with three FKs into two other tables that are all validated the same
    way (existence, via `SaveChangesAsync` catching `ForeignKeyViolation`), so the three FK
    constraints are explicitly named** (`fk_knowledge_relation_source_node_id`,
    `fk_knowledge_relation_relationship_type_id`, `fk_knowledge_relation_target_node_id`) instead of
    relying on Postgres's implicit `<table>_<column>_fkey` naming — `KnowledgeRelationRepository`
    pattern-matches on `PostgresException.ConstraintName` to know which one fired and picks the
    right message ("The specified source KnowledgeNode does not exist." vs. "...target
    KnowledgeNode..." vs. "...RelationshipType..."). `ConstraintName` alone can't disambiguate a
    reversed case, though: when a `KnowledgeNode` or `RelationshipType` is *deleted* while still
    referenced by a `KnowledgeRelation`, the violation is caught in `KnowledgeNodeRepository`/
    `RelationshipTypeRepository.SaveChangesAsync()` instead (whichever table the `DELETE` targets),
    and by the time it gets there the *only* FK involved is the one pointing back at
    `knowledge_relation` — so those two repositories disambiguate by
    `PostgresException.TableName` instead (`"knowledge_node"` vs. `"knowledge_relation"` for
    `KnowledgeNodeRepository`; plain `TableName: "knowledge_relation"` is enough for
    `RelationshipTypeRepository`, which had no FK-violation catch at all before this story since
    nothing referenced `RelationshipType` yet). Same underlying idea as the `ConstraintName` switch
    above — a Postgres string field on the caught `PostgresException` picks the right message — just
    keyed on whichever field actually distinguishes the cases at that call site.

## Testing (MnemoToad.Tests)
- **NUnit + Moq**, not xUnit — a deliberate switch, not the default `dotnet new` choice, so don't
  drift back to xUnit conventions (`[Fact]`, `Assert.Equal`) in new test files. Use `[TestFixture]`/
  `[Test]`/`[SetUp]` and `Assert.That(actual, Is.EqualTo(expected))`-style constraints.
- Three layers of coverage, from fastest/most isolated to closest-to-real:
  - **Controller tests** (`MnemoToad.Tests/Controllers/`) mock the repository interface directly with
    Moq (`new Mock<INodeTypeRepository>()`, `.Setup(...)`, `.Verify(...)`) — no service layer left to
    mock (see "API patterns" above). `ValidationException`-catch assertions check the returned
    `ObjectResult`'s `StatusCode` is `400` and its `Value` is a `ProblemDetails` with the expected
    `Detail`, matching what the controller actually returns (`Problem(...)`).
  - **Repository tests** (`MnemoToad.Tests/Repositories/`) exist for all four entities
    (`NodeTypeRepositoryTests`, `KnowledgeNodeRepositoryTests`, `RelationshipTypeRepositoryTests`,
    `KnowledgeRelationRepositoryTests`) and run query/CRUD assertions against a real EF Core SQLite
    (`DataSource=:memory:`) database, with constraint violations simulated separately (see
    `MockableAppDbContext` below) — this is the layer where the "let the DB decide" collapse
    described above actually gets exercised. **This was EF Core's InMemory provider until
    `DeleteAsync` switched to `ExecuteDeleteAsync` (see "API patterns" above)** — InMemory doesn't
    support `ExecuteDelete`/`ExecuteUpdate` at all (throws at runtime), while SQLite is a real
    relational provider and translates them to actual `DELETE`/`UPDATE` SQL. Note this doesn't buy
    *real* constraint enforcement in tests either way: `AppDbContext` has no `OnModelCreating` at
    all (no Fluent API, no navigation properties, no `[Index]` attributes) — every DB constraint
    (unique indexes, FKs) lives purely in the DbUp SQL scripts, never in the EF model, by design (see
    "Database" above). So constraint violations are still always simulated via
    `MockableAppDbContext`/`PostgresExceptionFactory`, exactly as before; the provider switch is
    purely so `ExecuteDelete`/`ExecuteUpdate` don't throw on the happy path.
  - **System tests** (`MnemoToad.Tests/SystemTests/`) send real HTTP requests through the full app
    pipeline via `WebApplicationFactory<Program>` — see below.
- `[SetUp]` creates a fresh mock/context/factory per test (not shared/static state), so tests can't
  leak setup between each other regardless of run order.
- **`MockableAppDbContext`** (`MnemoToad.Tests/TestSupport/MockableAppDbContext.cs`) is what makes
  repository (and system) tests possible without a real Postgres instance. It implements
  `IAppDbContext` as a decorator: the four `DbSet<T>` properties forward straight to a wrapped
  `IAppDbContext` (defaulting to a real `AppDbContext` on SQLite `:memory:`, via
  `SqliteAppDbContext.Create()` — which also hands back the open `SqliteConnection` so
  `MockableAppDbContext.Dispose()` can close it, since a SQLite in-memory database is destroyed the
  moment its connection closes, but swappable via its constructor), while `SaveChangesAsync()` and
  `ExecuteDeleteAsync<TEntity>()` each route through an internal `Mock<IAppDbContext>` that by
  default just forwards to the same wrapped context (e.g.
  `.Setup(db => db.SaveChangesAsync()).Returns(() => _wrapped.SaveChangesAsync())`). A test
  simulating a Postgres constraint violation on create/update calls `.ThrowOnSaveChanges(exception)`;
  one on delete calls `.ThrowOnExecuteDelete<TEntity>(exception)` (needs the closed generic type,
  since `ExecuteDeleteAsync<TEntity>` is generic and Moq setups are per closed type — the four
  `DbSet`-shaped default forwards in the constructor are set up the same way, once per entity type).
  Either re-`Setup()`s just that one call (last `Setup` wins) — everything else (real LINQ/async-LINQ
  execution, which Moq can't fake without an actual query provider behind it) keeps working
  unmodified. A repository test's `[SetUp]` is just
  `_db = new MockableAppDbContext(); _repository = new NodeTypeRepository(_db);` — no separate mock
  setup needed for the happy-path tests at all. `MnemoToad.Tests.csproj` pins
  `SQLitePCLRaw.bundle_e_sqlite3` to `3.0.5` explicitly — the version `Microsoft.EntityFrameworkCore.
  Sqlite` 10.0.10 pulls transitively (`2.1.11`) has a known high-severity advisory
  (`GHSA-2m69-gcr7-jv3q`).
- **A post-delete assertion in a test must query with `.AsNoTracking()`, not `FindAsync`.**
  `ExecuteDeleteAsync` bypasses the change tracker entirely (it's a direct SQL `DELETE`, not a
  tracked-entity removal), so an entity added earlier in the same test via `_db.NodeType.AddAsync(...)`
  stays cached in the context's tracker as `Unchanged` even after the row is really gone —
  `DbSet<T>.FindAsync` checks the tracker first and returns that stale cached instance without
  re-querying, making a real deletion look like it silently failed. `.AsNoTracking().FirstOrDefaultAsync(...)`
  forces an actual query against the database instead. This only bites tests (a single `AppDbContext`
  instance living across setup + act + assert in one test, or across a whole `MockedDbWebApplicationFactory`
  test since it's registered `AddSingleton` — see below); production controllers never re-fetch an
  entity they just deleted within the same request.
- **`PostgresExceptionFactory`** (`MnemoToad.Tests/TestSupport/PostgresExceptionFactory.cs`) builds
  the exact `DbUpdateException(PostgresException)` shape a repository's `SaveChangesAsync`/
  `ExecuteDeleteAsync` catches — `UniqueViolation(tableName:, constraintName:)` /
  `ForeignKeyViolation(tableName:, constraintName:)` return the `DbUpdateException` ready to throw
  directly, since every caller needed that exact wrapping anyway (this is also why `AppDbContext.
  ExecuteDeleteAsync` wraps the raw `PostgresException` it actually gets from Postgres into a
  `DbUpdateException` itself — so the real and simulated shapes match). `KnowledgeRelationRepository`
  needs `constraintName` to disambiguate its three FKs; `KnowledgeNodeRepository`/
  `RelationshipTypeRepository` need `tableName` to disambiguate a delete-time violation (referenced
  by a `KnowledgeRelation`) from a create-time one (see "Constraint-violation translation" above).
- **System tests** (`MnemoToad.Tests/SystemTests/`) exist for all four controllers
  (`NodeTypesControllerSystemTests`, `KnowledgeNodesControllerSystemTests`,
  `RelationshipTypesControllerSystemTests`, `KnowledgeRelationsControllerSystemTests`) and send real
  HTTP requests via `HttpClient` — not calling controller action methods directly. This matters
  because ASP.NET Core's automatic `[ApiController]` model-validation filter (DataAnnotations) only
  runs as part of the real MVC pipeline; a direct controller-method call bypasses
  routing/model-binding/filters entirely and can't exercise it, so this is the only place
  blank-field/empty-Guid validation gets verified at the .NET-test level (Karate is the other).
  - `Program.cs` has a trailing `public partial class Program { }` purely so the test assembly can
    reference the entry point — top-level statements otherwise generate an `internal` `Program`
    class, invisible outside `MnemoToad.Api`.
  - **`MockedDbWebApplicationFactory`**
    (`MnemoToad.Tests/TestSupport/MockedDbWebApplicationFactory.cs`) is a `WebApplicationFactory<Program>`
    that overrides only `IAppDbContext` in `ConfigureWebHost`, pointing it at a `MockableAppDbContext`
    (exposed as `.Db`, so tests can call `.Db.ThrowOnSaveChanges(...)`/`.Db.ThrowOnExecuteDelete<T>(...)`)
    — routing, DataAnnotations
    validation, controllers, and JSON serialization are all the real thing. **It registers
    `IAppDbContext` as `AddSingleton`, not `AddScoped`** — ASP.NET Core creates a new DI scope per
    HTTP request and disposes scoped disposables when that scope ends, so registering it `AddScoped`
    meant the first request's teardown disposed the shared `Db` and broke every request after it in
    the same test; `AddSingleton` ties its lifetime to the factory/host instead, matching what a test
    actually needs (the same `Db` persisting across multiple requests within one test).
  - **`DbFixtures`** (`MnemoToad.Tests/TestSupport/DbFixtures.cs`) — `IAppDbContext` extension methods
    (`CreateNodeTypeAsync`, `CreateKnowledgeNodeAsync`, `CreateRelationshipTypeAsync`,
    `CreateKnowledgeRelationAsync`) that insert directly into the in-memory database. System tests use
    these for setup-only preconditions (e.g. a `NodeType` a `KnowledgeNode` test needs to reference)
    and reserve real HTTP calls for whichever endpoint the test is actually exercising — the same
    "only call the create-helper when creation is just setup for testing something else" rule Karate's
    `fixtures.js` pattern already follows (see "Karate tests" below). An earlier version of these
    system tests created setup data via real HTTP `POST` calls too, before that rule was applied here
    as well.

## Karate tests
- General `TestRunner.java` scans all features under `classpath:com/mnemotoad` (not one runner per
  feature). Tags filtered via `-Dkarate.tags` system property — a single expression string, e.g.
  `"@Regression,@Smoke"` (comma = OR). Don't split it into multiple `.tags(...)` list elements in
  `TestRunner.java`; Karate treats each separate list element as AND'd together, which silently
  requires every listed tag on the same scenario instead of matching any of them.
- `@Smoke` / `@Regression` tags. Actual file is `karate.yml` (not `karate-tests.yml`). Runs via
  `pipeline.yml` (`@Smoke`/`azure`) whenever `api`, `data`, or `karate` changed; nightly schedule
  (commented out, not yet enabled) would run `@Regression`; `workflow_dispatch` is parameterized.
- Per-entity package convention (e.g. `nodetype/`): `<entity>.feature` (the real CRUD tests),
  `create-<entity>.feature` (reusable setup-only helper), `delete-<entity>.feature` (cleanup
  helper), `fixtures.js` (entity-specific create/delete strategy, see below), all same package,
  referenced by relative path. `common/util.js` (cross-package, `classpath:` reference) generates
  unique test data names (`ZZ_Karate_<label>_<uuid>`); `common/fixture-container.js` (also
  cross-package) is the generic tracked-entity container described below.
- **Rule: only call the `create-<entity>.feature` helper when creation is just setup for testing
  something else.** Scenarios actually testing the create endpoint call the API directly.
- **`common/fixture-container.js` + per-package `fixtures.js` pattern**: `fixture-container.js` is
  a generic factory — `function(strategies) {...}` — that knows nothing about NodeType or
  KnowledgeNode specifically. Given `{ create, remove }` strategy functions (each operating on a
  single entity/id), it returns a stateful container exposing a uniform interface: `create(overrides)`
  (calls the strategy, tracks the returned id), `stageForCleanup(id)` (tracks an id that was created
  some other way, e.g. a raw API call in a scenario body), and `cleanup()` (calls the remove
  strategy for every tracked id, and — this is the point of doing it as a container rather than a
  loop inlined in each package — **removes each id from its internal list as soon as that id's
  delete succeeds**, leaving only the ones that failed; see its `remaining` array, not a `splice`
  during iteration). The tracked-ids array lives entirely inside `fixture-container.js`'s own
  closure, created fresh per invocation. Each entity package's `fixtures.js` is now just
  configuration: it defines that package's `create`/`remove` strategies (the actual
  `karate.call('classpath:.../create-<entity>.feature', ...)` /
  `karate.call('classpath:.../delete-<entity>.feature', ...)` calls) and hands them to
  `fixture-container.js`, obtained via `karate.read(...)` (the JS-context equivalent of the
  `read()` keyword) since a `.js` file's own top level is plain JS, not Karate DSL. A `Background`
  wires the result directly, no per-package function names needed since the interface is uniform
  across entities: `* def nodeTypeFixtures = call read('fixtures.js')` then
  `* def createNodeType = nodeTypeFixtures.create` and
  `* configure afterScenario = nodeTypeFixtures.cleanup`. A scenario that creates an entity via a
  raw API call (not through `create<Entity>`) calls `nodeTypeFixtures.stageForCleanup(response.id)`
  for cleanup. This replaced an earlier version where each package's `fixtures.js` hand-rolled its
  own `createdIds` array and its own non-self-pruning cleanup loop — that logic now exists exactly
  once, in `fixture-container.js`, and every entity gets it by supplying two functions.
- **`knowledgenode/` package reuses `nodetype/`'s create/delete features directly across
  packages** (via `classpath:com/mnemotoad/nodetype/create-nodetype.feature` /
  `classpath:com/mnemotoad/nodetype/delete-nodetype.feature`, and its `Background` also builds its
  own `nodeTypeFixtures` from `classpath:com/mnemotoad/nodetype/fixtures.js`) rather than
  duplicating NodeType create/cleanup logic inside `knowledgenode/` — first cross-package
  `.feature`-to-`.feature` reference (`common/util.js` was already cross-package, but that's a
  plain JS file). Don't reintroduce a copy-pasted NodeType strategy inside `knowledgenode/fixtures.js`
  when this pattern gets extended to a third entity.
  - **`knowledge_node.node_type_id` is a required FK, and `nodeTypeId` is a required argument to
    `create-knowledgenode.feature`** (asserted with `* assert nodeTypeId` — fails fast with a clear
    message if a caller forgets it) — there is deliberately no auto-provisioning fallback that
    creates a throwaway `NodeType` when one isn't passed in. An earlier version did auto-provision
    one, which meant `knowledgenode/fixtures.js` had to depend on `nodetype/fixtures.js` just to
    stage the auto-created `NodeType` for cleanup; removing the fallback removed that dependency
    too — `knowledgenode/fixtures.js` now takes no constructor argument and knows nothing about
    NodeType at all. Every scenario in `knowledgenode.feature` that needs a `KnowledgeNode` now
    explicitly calls `createNodeType()` first and passes its id in as `overrides.nodeTypeId`.
  - `knowledgenode.feature`'s `afterScenario` still calls `knowledgeNodeFixtures.cleanup()`
    **before** `nodeTypeFixtures.cleanup()` — order matters here, not just cosmetic, since the FK on
    `node_type_id` would reject deleting a still-referenced `NodeType`; this ordering is now just
    "clean up dependents before dependencies" rather than anything to do with auto-provisioning.
  - `knowledgenode.feature` includes a "Reject deleting a node type that is referenced by a
    knowledge node" scenario that calls the `/nodeTypes` DELETE endpoint (not `/nodes`) — that's
    deliberate, it's exercising `NodeTypeRepository`'s delete-guard from the `NodeType` side, using a
    `KnowledgeNode` as the reference. Lives in `knowledgenode/` rather than `nodetype/` since it only
    became testable once `KnowledgeNode` existed.
- **`knowledgerelation/` extends the same cross-package reuse to a third and fourth
  entity** — its `Background` builds `nodeTypeFixtures`, `knowledgeNodeFixtures`, and
  `relationshipTypeFixtures` from their existing `classpath:.../fixtures.js` files (no copy-pasted
  create/delete logic for any of them), alongside its own `knowledgeRelationFixtures`.
  `afterScenario` cleans up in dependency order: `knowledgeRelationFixtures` first (it references
  both nodes and the relationship type), then `knowledgeNodeFixtures`, then `nodeTypeFixtures` and
  `relationshipTypeFixtures` (order between those last two doesn't matter, neither references the
  other). `knowledgerelation.feature` owns the "Reject deleting a knowledge node that is referenced
  by a relation" scenario (there's no other natural home for it — it isn't a pre-existing
  placeholder anywhere else). **The RelationshipType-side delete-guard scenario is different: it
  went back into `relationshiptype.feature` itself**, un-ignoring and implementing the
  `@ignore`d placeholder (with the "no Relationship table exists yet" TODO) that already lived
  there, rather than moving it to `knowledgerelation.feature` the way `knowledgenode.feature` holds
  NodeType's. `relationshiptype.feature`'s `Background` now also wires `nodeTypeFixtures`/
  `knowledgeNodeFixtures`/`knowledgeRelationFixtures` (same cross-package pattern, same cleanup
  ordering) purely to support that one scenario. Don't read the `knowledgenode.feature`-holds-
  NodeType's-guard case as a rule that a referencing entity's delete-guard test always lives in the
  referenced-from package — that was specific to how that scenario was introduced, not a
  generalizable convention.
- No passthru/direct-DB-query endpoint yet — tests validate purely through the API's own responses.
  Add one if a future story needs to assert something the API doesn't surface (e.g. cascade
  behavior at the DB level). Concrete case in hand: `knowledge_node.created_utc`/
  `modified_utc` are DB-populated and not returned by the API at all (see "Database" section above)
  — no current Karate test can assert they're actually set/updated without one. The .NET-side
  equivalent of this problem is solved by `DbFixtures`/`MockedDbWebApplicationFactory` in
  `MnemoToad.Tests` (see "Testing" above), since those seed straight into the in-memory DB rather
  than through the API — a Karate-side equivalent (a passthru API, or moving some endpoints to
  test-server-only) is wanted eventually but not planned for a while.
